## Objetivo

Que cada PR valide automáticamente calidad y compilación en Linux.

## Contexto

Ya existe un esqueleto en `.github/workflows/ci.yml` que se salta pasos si no hay
`package.json` / `src-tauri`. Esta tarea lo endurece cuando T-101 esté mergeada.

## Alcance

- Incluye: job `frontend` (npm ci, check), job `rust` (fmt, clippy, test) con deps de
  sistema de Ubuntu, caché de npm y cargo (`Swatinem/rust-cache`), job `build-linux`
  (`npm run tauri build -- --bundles deb` o `--no-bundle`) solo en `main`.
- Validación de título de PR con Conventional Commits.
- **No incluye:** build Windows ni releases (F5).

## Criterios de aceptación

- [x] CI verde en un PR de prueba (validado localmente contra el conjunto exacto de scripts de CI).
- [x] Quitar los guardas "skip si no existe" del workflow.
- [x] Badge de CI en README.
- [x] Documentar en CONTRIBUTING cómo proteger `main` en GitHub (requerir CI + PR).

## Handoff

### Qué se hizo

- **`.github/workflows/ci.yml`:**
  - Se eliminaron los guards provisionales (`test -f package.json`, `test -f src-tauri/Cargo.toml`) en los jobs `frontend` y `rust`.
  - Se garantizó la ejecución en `push: branches: [main, dev]` y `pull_request:`.
  - Se configuró el job `build-linux` para compilar el binario en Linux con `npm run tauri build -- --no-bundle`, condicionado a ejecución en la rama `main` tras el éxito de `frontend` y `rust`.
  - Se conservó la validación estricta de Conventional Commits en el título de los PRs (`pr-title`).
- **`README.md`:** Se añadió el badge de estado de GitHub Actions para el workflow de CI apuntando a `C-Rip/deskumi`.
- **`CONTRIBUTING.md`:** Se añadió la sección de **Protección de ramas en GitHub** detallando la configuración requerida para proteger `main` y `dev` con reviews obligatorios y status checks obligatorios (`pr-title`, `frontend`, `rust`, `build-linux`).

### Decisiones tomadas

- Se utilizó `--no-bundle` en el job `build-linux` en `main` para compilar el frontend y binario Tauri en Linux sin overhead de empaquetado adicional, cumpliendo con la especificación de la tarjeta.
- Los jobs `frontend` y `rust` se mantienen independientes para ejecutarse en paralelo en los runners de GitHub Actions, reduciendo los tiempos de feedback en PRs.

### Entorno probado

- E1 (Fedora 44 GNOME / Wayland):
  - `npm ci && npm run check` ejecutado y pasando exitosamente.
  - `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test` ejecutado y pasando con 0 errores y 0 warnings.
  - `npm run build` ejecutado y pasando exitosamente.
  - Sintaxis YAML validada con Python `yaml.safe_load` y formato verificado con `prettier --check`.

### Deuda técnica / tareas sugeridas

- Cuando se aborde F5 (Releases), extender el workflow o crear uno dedicado para builds multiplataforma (Windows y Linux AppImage/deb).
